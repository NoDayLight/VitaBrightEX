# VitaBrightEX pseudo-v1.4 architecture

Pseudo-v1.4 treats brightness control as the core product and every less-established display mutation as an optional capability. The correct failure mode is loss of an enhancement, never loss of LiveArea.

## Boot contract

`module_start()` reads firmware/model once, initializes status and the state-transition mutex, initializes safe configuration defaults, attempts an authoritative config load, starts exactly one brightness backend, probes optional verified capabilities, and always fails open at the module boundary. A malformed authoritative config is reported as `VBE_ERR_CONFIG`; initialized defaults remain in use rather than hiding the parse failure or blocking boot.

No polling thread, timer, periodic file read, framebuffer interception, per-frame callback or software pixel-processing path is introduced.

## Serialization model

One kernel mutex serializes reload/editor/status transitions. User writes follow:

`checked user copy -> temporary candidate -> validation -> state lock -> transactional hardware change -> commit/rollback`

Hook callbacks do not take the mutex. Teardown removes hooks before invalidating state/function pointers visible to them.

## Authoritative text-parser contract

Physical PCH-2000 testing exposed an important v1.4 defect in the previous software gate: the packaged LCD LUT contained descriptive comments longer than the kernel's `char line[64]`, while the Python CI validator ignored comments without that limit. Workflow #114 therefore declared an authoritative file valid that the exact production SKPRX rejected before SceLcd layout validation.

The parser/CI divergence is treated as a release-blocking contract failure rather than a bad comment. The current architecture therefore uses production parser cores as CI executables instead of maintaining a separate Python grammar.

### Newline contract

All authoritative text parsers share `text_stream.c` as a strict byte-stream newline decoder:

- `LF` is one logical newline.
- `CRLF` is one logical newline.
- `CR` followed by a non-`LF` byte is malformed.
- a terminal/lone `CR` at EOF is malformed.
- `CR` is never silently discarded inside a decimal token, hexadecimal byte or config value.

This specifically rejects transformations such as `2\r55 -> 255` and `A\rF -> AF` while retaining normal Windows CRLF files.

### LCD/OLED LUT grammar

LCD and OLED use portable streaming C state machines with no fixed physical-comment-line buffer. Once a full-line `#` or `;` comment is recognized, the comment body is discarded while streaming, so comment length is not an input limit.

LCD data remains strict: exactly 17 unsigned decimal bytes, each `0..255`, monotonic nondecreasing, optional horizontal whitespace and inline comment, LF/CRLF, and EOF without a final newline. OLED remains exactly 17 rows of exactly 21 two-digit hexadecimal bytes with controlled separators/comments.

A present-but-malformed authoritative source is terminal failure. It is never hidden by a valid lower-priority source. Only failure to open the preferred source permits documented fallback.

### Config grammar

The Vita-specific `config.c` layer now performs only `ksceIoOpen`/chunked `ksceIoRead`/`ksceIoClose` and feeds the exact portable `config_parser.c` core used by host CI. Full-line `#` and `;` comments are unbounded streams. Known directives are bounded by the destination representation; an overlong known value rejects the authoritative config rather than truncating it or allowing a tail to become a second directive.

Known integer and floating-point values use exact-token parsing. Numeric suffix garbage such as `6500garbage` or `1.2nonsense` is rejected. Parsed extreme values are safely saturated and then clamped to the documented configuration range. Unknown keys and lines without `=` are ignored for forward/backward compatibility. An empty numeric value is malformed; an empty `panel_lut_path` is valid. If a known key occurs more than once, the last valid occurrence wins.

### Executable CI proof

`tools/validate_packaged_assets.py` byte-compares source/package assets, then compiles and executes three host regressions:

- `tests/lut_parser_host.c` with the exact production LCD/OLED parser sources and shared newline decoder;
- `tests/config_parser_host.c` with the exact production config parser and shared newline decoder;
- `tests/status_error_host.c` with the exact error-domain precedence core.

LUT cases include the exact shipped assets, 16-KiB comments, malformed long data, LF/CRLF, interior/lone CR rejection, EOF-without-final-newline, count/range/monotonicity failures and OLED CR-in-byte rejection. Config cases include the exact packaged config, long `#`/`;` comments, overlong known directives, valid-looking tails after an overlong directive, LF/CRLF, interior/lone CR, whitespace, unknown/known keys, missing `=`, empty values, extreme/clamped numbers, suffix garbage and duplicate keys.

`tools/verify_parser_contract.py` remains only a cheap structural tripwire: it checks that production I/O paths still feed those portable cores and that fixed-line parser patterns do not return. Semantic proof belongs to the compiled host tests.

## LCD brightness transaction

PCH-2000 startup acquires:

1. validated authoritative LUT candidate
2. required `SceLcd` exports by NID
3. firmware whitelist/layout candidate
4. runtime verification of the exact stock 17-byte table signature at the inherited segment-0 offset
5. table injection
6. brightness hook
7. ScePower maximum-brightness hook
8. checked current-brightness reapply
9. active-state commit

Any failure unwinds acquired resources. Negative getter results are never converted into unsigned hardware writes. A live LUT replacement preserves the last committed table and attempts rollback if the replacement transaction fails.

The LCD representation is monotonic nondecreasing in the driver's logical brightness direction. The default extended table is:

```text
1 3 5 8 13 20 29 41 57 76 95 116 137 161 190 220 255
```

### Raw-layout policy and physical evidence

Inherited candidates remain 3.60 -> `0x1B00` and 3.65/3.67/3.68/3.69/3.70 -> `0x1B48`. 3.71-3.74 are not guessed to share this layout. Every accepted candidate must still contain the exact Sony stock signature before injection.

On 2026-09-12 the mandatory physical PCH-2000 / 3.65 Ensō target (`0x03650000`) passed that production runtime gate at segment-0 `0x1B48`: after removal of the separate parser blocker, status became `firmware_layout/core/table/brightness_hook/power_limit_hook=active` with `last_error=0`. Stock-vs-extended A/B testing also confirmed the ascending table direction and extended lower luminance.

This is **physical runtime exact-signature evidence**, not static decrypted-binary verification. Static ELF/segment evidence remains pending and is tracked in [`FIRMWARE-LAYOUT-VERIFICATION.md`](FIRMWARE-LAYOUT-VERIFICATION.md).

## LCD inactivity-dim path

The hook only intervenes when the OS requests brightness `1`. It reads current logical brightness, derives table index, and suppresses the request only when the corresponding extended table value is below `25`, preventing a nominal dim request from making an already-darker display brighter.

Physical testing has passed midpoint dimming and observed low-level behavior consistent with this rule. True maximum-slider behavior remains open. Diagnostic builds log `[LCD:DIM]` with prior raw value, derived index/table value and allow decision, plus `[LCD:POWER]` maximum-brightness requests. Release builds compile `LOG(...)` to a statement-safe no-op.

## OLED brightness transaction

PCH-1000 startup requires a whitelisted firmware family, resolves brightness/DDB exports, requires successful DDB, selects the upstream panel mapping, validates the inherited loaded-module table address, loads a complete 17x21-byte candidate, injects it, installs brightness/power hooks, performs a checked current-brightness reapply and commits only after all required stages succeed.

Panel mapping remains DDB low byte 4 -> `0x1AB8`, low byte 5 -> `0x1C20`, and low byte 6/other successfully read types -> `0x1E00`. A failed DDB read is never treated as a default panel. Live replacement preserves the previous table and attempts rollback.

The 21 bytes of each OLED row are seven RGB gamma-reference triplets. The display driver's register-code -> physical-voltage/transfer function is not independently established, so v1.4 does not reintroduce guessed white-point/RGB-bias/night-mode arithmetic. Panel-specific LUTs and explicit raw editor edits remain supported.

## Authoritative LUT persistence

LUT state has one authority at a time. The backend records the exact source path that produced the committed table. Editor changes go through checked kernel syscalls. Square Save calls a kernel persistence syscall, which writes a same-directory temporary file, syncs/closes it, then renames it over the authoritative target. This preserves custom OLED overrides and `ur0`/`ux0` source identity across edit -> save -> reload.

## Screen-filter capability boundary

The v1.3 private `0x0FCBF457` call is gone. VitaSDK documents `ksceIftuCsc()` NID `0x67E37EFC` as an explicit source/destination conversion API, not evidence of a persistent active-scanout matrix setter. Hardware invert is supported when its SceDisplay export resolves; arbitrary persistent CCT/contrast/brightness CSC, nonlinear transfer and guessed OLED gamma arithmetic remain unsupported.

## Panel color-space capability

Matched panel Get/SetDisplayColorSpaceMode exports provide one backend-neutral session capability. v1.4 snapshots original mode, accepts only 0/1, avoids redundant writes, performs write + immediate read-back verification, and restores firmware-owned state on teardown. There is no registry mutation or continuous workload.

## Status ABI, error ownership and provenance

`VitaBrightStatus` remains **ABI v2 with its original size/layout**. This is deliberate so an already-built ABI-v2 editor cannot overrun a smaller user buffer. Its `last_error/detail` fields are now a deterministic summary rather than one globally mutable slot.

Independent internal error domains are retained for synchronization, brightness, configuration, panel color-space, filter and user input. The legacy summary precedence is synchronization -> brightness -> configuration -> color-space -> filter -> input. A success clears only the domain it actually repaired. Consequently, toggling color-space or successfully saving a LUT cannot erase an unresolved authoritative config failure.

A separate additive `VitaBrightDiagnostics` ABI v1 and `vitabrightGetDiagnostics()` expose all domain slots without changing the status-v2 structure. `tests/status_error_host.c` behaviorally verifies retention and precedence.

Development builds also export `vitabrightGetBuildId()`. CMake derives an 8-character build ID from the actual `GITHUB_SHA` in Actions or `git rev-parse --short=8 HEAD` locally. The editor embeds its own ID and displays plugin/editor IDs plus `MATCH` or `MISMATCH`. This makes stale editor/kernel pairings visible on-device without adding fields to status ABI v2.

## Deployment contract

VitaShell FTP destinations are absolute mount paths. Project CMake defines one canonical root and constructs `//ur0:` / `//ux0:` destinations from it while using `curl --ftp-method nocwd`. Relative-looking `...:1337/ur0:/...` forms are forbidden by the source contract. User-facing hardware commands use the same proven absolute form, e.g. `ftp://192.168.1.131:1337//ur0:/tai/...`.

The kernel plugin and the editor are separate components. Replacing files under `ur0:tai` does not update an installed VPK. Hardware-test bundles therefore include both components, a commit marker, per-file SHA-256 manifest and an explicit bundle README. Tests that depend on provenance/diagnostics/current UI wording require installing the matching VPK first.

## Build/asset verification and hardware state

CI enforces source invariants, structural parser/deployment contracts, exact source/package identity, compiled production LUT/config/error-state regression tests, current VitaSDK release + diagnostic builds with warnings as errors, generated syscall stubs and the matching editor build.

The first mandatory isolated cold boot on PCH-2000 / 3.65 Ensō passed and did not reproduce the v1.3 hang. The same test exposed the original parser/CI defect, demonstrating why a green build is not itself hardware verification.
